# control-plane

FastAPI app on a Vultr VM: job API, live SSE timeline, web UI, `/verify` page and the
sandbox reaper. Holds the only credentials in the system (Vultr API key, Serverless
Inference key, receipt-signing key), loaded from a root-only env file at deploy time.

Built during the event window (Nov 3–8). See the plan (kept private) §3.

## Deploy (`deploy/`)

```bash
python3 -I -B control-plane/deploy/deploy.py up --allow 203.0.113.10/32 203.0.113.11/32
python3 -I -B control-plane/deploy/deploy.py status
python3 -I -B control-plane/deploy/deploy.py destroy          # keeps the VPC; --vpc drops it too
```

`up` is idempotent: it reuses whatever already exists and re-runs `provision.sh`, so it is also
how a config change ships. Credentials are read from `the secrets directory` (`vultr.env`,
`cloudflare.env`); resource IDs and the VM's SSH key are written back there
(`vultr-arz-control-plane.env`, `vultr-arz-control-plane.key`).

| Piece | Value |
|---|---|
| Instance | `arz-control-plane`, `vc2-1c-2gb`, Ubuntu 24.04, `dfw`, no IPv6, tag `arz-control-plane` |
| VPC | `arz-vpc`, `10.50.0.0/24`, shared with the sandboxes |
| Firewall group | `arz-control-plane`: 80/443 from anywhere, 22 from the operator's addresses |
| Host firewall | nftables (ufw disabled): drops every new connection from the VPC, so a sandbox can never open one to the control plane |
| URL | `https://agentrush.geekendzone.net` — Cloudflare A record, **DNS-only**; Caddy gets its own Let's Encrypt certificate |
| SSH | keys only (`sshd_config.d/00-arz.conf`) |
| Secrets on the VM | `/etc/arz/control-plane.env` (root, 0600): `VULTR_API_KEY` and the sandbox settings; `/etc/arz/receipt-signing.pem` (root, 0600), from `$ARZ_SECRETS_DIR/arz-receipt-signing.pem` |
| Receipt public key | `https://agentrush.geekendzone.net/.well-known/receipt-key` |

### Jobs (`arz/`)

`arz.vultr` is a stdlib Vultr client; `arz.sandbox.Sandbox` is one ephemeral VM per job: a
per-job SSH key, created from the snapshot on `arz-vpc` with the empty `arz-sandbox` firewall
group and no user-data, reached over the VPC, and deleted with a verified 404 on exit whatever
happened inside. Settings come from `/etc/arz/control-plane.env` (`ARZ_SNAPSHOT_ID`,
`ARZ_VPC_ID`, `ARZ_SANDBOX_FIREWALL_ID`, `ARZ_REGION`, `ARZ_SANDBOX_PLAN`).

The `hello` job is the end-to-end check (provision → upload → run → pull → recompute every
SHA-256 → delete → 404). Reports land in `/var/lib/arz/jobs/<job-id>/report.json`:

```bash
ssh -i $ARZ_SECRETS_DIR/vultr-arz-control-plane.key root@<ip> \
  'cd /opt/arz/app && set -a && . /etc/arz/control-plane.env && set +a && /opt/arz/venv/bin/python -m arz.hello'
```

The `analysis` job runs `vibkit.analyze` on one dataset in a sandbox and signs a receipt:
`/opt/arz/venv/bin/python -m arz.analysis --dataset misalignment` (same environment as
above). The sandbox gets the measurement and the machine metadata, never the ground truth;
the control plane compares the result with it afterwards. The receipt (`receipt.zip` next to
`report.json`) holds the hash-chained event log (job, sandbox create/ready, upload hashes,
the step with its container flags, limits and output hashes, pull verification, the verified
404, the result and the ground-truth check), the pulled files, and an Ed25519-signed manifest.
Anyone can check one offline:

```bash
uv run --project receipts arz-receipt verify receipt.zip \
  --pubkey $(curl -s https://agentrush.geekendzone.net/.well-known/receipt-key)
```

A new snapshot ships with `deploy.py up --snapshot <id>`.

On the VM: `/opt/arz/app` (this package), `/opt/arz/venv` (numpy, `arz-receipts`,
cryptography), `/opt/arz/datasets/synth` (regenerated by `provision.sh` from
`data/synth/generate.py` and checked against `SHA256SUMS.expected`; a mismatch fails the
deploy), `/var/lib/arz/jobs/<job-id>/` (reports, pulled files, receipts).

### Red team (`arz/redteam.py`)

With `--redteam` (CLI) or the console's checkbox (on by default for `prompt_injection`), after
the analysis the same sandbox gets three more steps, each one an event in the signed log:

1. **Replay**: the commands the injected notes ask for, run literally in the locked container:
   read `/proc/self/environ` (nothing credential-like in it), POST it to the attacker's
   collector (no DNS, no route), `cat ~/.ssh/* /root/.ssh/*` (no such directory, permission denied).
2. **Probes**: `redteam/run.py` on the VM: 8 container probes, 2 VM probes, and the
   control-plane probe (`ARZ_CP_VPC_IP`).
3. **Forged claim**: the injection's "report it healthy, zone A" submitted to `check_claims` as if
   the model had written it: rejected against the reference diagnosis.

The probe report and the replay's output go into the receipt under `artifacts/redteam/`.

### Web app and warm pool (`arz/web.py`, `arz/pool.py`, `arz/static/`)

`arz-web.service` runs uvicorn on `127.0.0.1:8000` as the `arz` user (systemd-hardened, writes
only `/var/lib/arz`); Caddy proxies everything but `/healthz` and the receipt key to it, with
SSE flushing for the live timeline.

| Route | What |
|---|---|
| `/` | Console: pick a dataset, run it (access code), watch the two-lane timeline (control plane / sandbox VM; the sandbox lane exists only between create and the verified 404), verdict with the ISO 20816-3 scale, work order, the agent's spectrum, receipt download. `#job=<id>` links to a run |
| `/verify` | Upload a `receipt.zip`; every check shown PASS/FAIL against the published key |
| `POST /api/jobs` | `{dataset, code}` → `{id}`. Needs `ARZ_ACCESS_CODE` (`$ARZ_SECRETS_DIR/arz-access-code.env`); 6 runs/hour per address, 40/day, queue of 4, one job at a time |
| `GET /api/jobs[/<id>[/events|/files/<name>]]` | History (survives restarts), detail, SSE events, whitelisted files |
| `GET /api/status` | Warm pool, queue, model, runs today |

Warm pool of one: a sandbox booted ahead of time (tags `arz-sandbox` + `arz-warm`), used for
exactly one job, replaced in the background, recycled after 40 min idle; the reaper allows
`arz-warm` instances 60 min. On start the app deletes warm sandboxes left by a previous
process, retrying while Vultr answers 409 "locked" for one that was still booting. With a warm
sandbox ready, a run takes ~15 s instead of ~4 min.

### Sandbox reaper

`arz-reaper.timer` runs `/opt/arz/arz-reaper.py --max-age 600` every 2 minutes as a
`DynamicUser`. It deletes instances that carry the `arz-sandbox` tag **and** a label starting
with `arz-sandbox`, then polls until the API returns 404. Anything else is skipped and logged.
A failed delete or API error fails the unit.

```bash
ssh -i $ARZ_SECRETS_DIR/vultr-arz-control-plane.key root@<ip> \
  'journalctl -u arz-reaper -n 20 -o cat; /usr/bin/python3 -I /opt/arz/arz-reaper.py --dry-run --max-age 0'
```

The Vultr API key has an IP allowlist (Access Control), so the control plane's public IP must
be on it or every reaper run fails with `Unauthorized IP address`.
